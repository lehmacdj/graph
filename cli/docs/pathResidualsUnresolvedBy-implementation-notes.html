§1

The property-2 ambiguity finding

Property 2 demands: after deleting one edge e from a graph that resolves the path, the residual computed against graph − e must itself fully resolve in the graph containing only e. The residual must be exactly the removed edge’s contribution — much stronger than the §3 invariant (which properties 1 and 3 test, and which holds for these instances).

Some generated instances make that unsatisfiable: graph − e can contain two structurally symmetric single-edge residuals, both correct under the §3 invariant, of identical size, with no information distinguishing them — and only one matches the removed edge.

Minimal counterexample (found by shrinking)

@F/@f in the root’s exclusion set are inert shrinking leftovers — they never coincide with any node involved.

Both candidates mint exactly one edge and both make the original path resolve (verified in both directions). graph − e is perfectly symmetric between them; only knowing which edge was removed breaks the tie, and that information is not part of the function’s input. The same shape recurs with sequence steps instead of loops: a forward self-loop match vs. a backward-recoverable seam, e.g. ~c/|bar where ~c coincidentally matches a root-loop edge @1H>"c">@1H while the true seam edge @xho>"c">@1H was the one removed.

Why a tie-break cannot fix it

The local situation — “the forward pass matched something, and the backward pass also makes progress” — also occurs in unit tests, and they demand forward-keeping answers; some property-2 instances demand the opposite answer on locally identical evidence:

instancelocal evidencerequired answerrequired by
[a/|b]>@4 in [@1>"a">@2, @3>"b">@4] fwd: a matched, at @2; bwd: b matched, from @3 keep the fwd match, re-mint the suffix: [@2<b]>@4, not [a]>@3 unit test (“unchanged when unmatched”)
@[a/|d/|~c/|~b] in [@1>"a">@2, @2>"d">@2, @1>"b">@2, @2>"c">@3] fwd: d matched by a genuine self-loop @2>"d">@2; bwd: ~b progresses keep the self-loop fwd match: [@2<~c]>@2 unit test (“don’t meet up in middle”)
property-2 instance (~c/|bar shape above) fwd: ~c matched by a coincidental self-loop @1H>"c">@1H; bwd: seam recoverable trust the bwd seam (the removed edge was the seam @xho>"c">@1H) property 2

Rows 2 and 3 present the matcher with indistinguishable local evidence but need opposite choices. The one discriminator consistent with all unit tests is implemented (prefer the backward seam only when every forward match was frontier-preserving and the backward pass was fully rolled back — §2, decision 8). It fixed the most common collision class, but the residual ambiguity above survives any deterministic rule.

Root cause & ways out

The coincidences come from genTransitionLabel’s 11-word pool: reused labels inside one path make unrelated edges (especially self-loops minted for pointlike loops) match other occurrences’ steps.

iWeaken property 2 Require resolvesIn (graphMinusEdge <> instantiate residual) instead of resolution in {e} — property 3 restricted to singleton removals, unambiguous (and already covered by property 3).
iiUnique labels Make the generator label each transition occurrence uniquely (or precondition property 2 on label-distinct paths), removing the collision source.
iiiAccept & pin Accept the flake rate (~1 per few hundred cases) and fix the QuickCheck seed.
§2

Eleven ambiguous implementation decisions

Places where neither the spec nor the tests determine the behavior, and what was chosen. All choices are exercised by the property tests, so changing them later should be guarded by those. Examples marked prop are only exercised by the property tests; the rest come from the unit suite.

1Zero-consumption loop gaps are position-dependenta loop consumed zero steps

A loop that consumed nothing deconstructs at root positions but stays attached to the pointlike at midpoint positions. The spec describes only the deconstruction; the position split is inferred from the tests and generalized to unseen combinations (e.g. target loops behave like midpoints).

examples 
root:      [@1>"b">@3, @2>"a">@3]  ⊢  [@2[c]<a & @1<b]  ⇒  [@2<c]>@2
midpoint:  [@1>"a">@2, @2>"x">@3]  ⊢  [a /@[x]| b]      ⇒  [@2[x]<b]
2Conjunction vs. union for multi-NID gapsone gap, several frontier NIDs

A forward fan-out gap becomes intersected root branches of one deterministic path, while a multi-NID backward gap becomes separate union members — even though the shapes are isomorphic. Backward alternatives are additionally never merged with any other gap (the alone flag), since merging alternatives of one gap would wrongly conjoin them.

examples 
fwd:  [@1>"a">@2, @1>"a">@3]  ⊢  [a/|b]      ⇒  [@2<b & @3<b]
bwd:  [@2>"c">@1, @3>"c">@1]  ⊢  @[a/|b/|c]  ⇒  [@2<~b /| ~a]>@1 + [@3<~b /| ~a]>@1
3Roots that can never unify are dropped, not keptroot JoinPoint excludes the start NID

resolveNPath resolves each root of a multi-root path independently (its result is a union over roots), so resolvesIn is true even when a root is a JoinPoint excluding the start NID. Since creating edges can never help such a root, its branches are omitted from the residual; a path consisting only of such roots still returns unchanged (no progress), which is the §8 behavior. The spec’s “unchanged” wording only contemplates the single-root case. prop

4Nested roots with Unanchored targets are treated as join pointsnested rooted root, Unanchored target

The §3 carve-out exempts only the top-level target. A nested rooted root with an Unanchored target must make its branches meet for the invariant to hold, so internally it is rewritten to JoinPoint ∅, its junction may be pinned, and outer branches resume from the pinned NID. Justified by §5’s “concrete resume points are required structure, not anchor pinning”; without this, property 3 fails. prop

5Join pinning beyond §5’s rulejoin target; no resolved branches agree

§5 pins a JoinPoint target to “the NID the resolved branches agreed on”. Extensions needed by the properties:

Reach pinning — a branch that gapped early but whose suffix fully resolves to the target reports that terminal (“reach”); when no branch fully lands, the join pins on agreeing reaches. Loop/cost search — when nothing lands or reaches, every admissible node is evaluated as the join (re-aiming all branches at it) and the one minimizing total residual weight wins. Among meet candidates, prefer one where the target’s own loops resolve (otherwise property 1 fails when branch fan-out makes the meet ambiguous). The spec’s disagreement rule (resolved branches disagree ⇒ demote, no pin) is preserved and takes precedence.

basic agree-rule 
[@1>"a">@2]  ⊢  [@<a & @<b & @<c]>@  ⇒  [@1<b & @1<c]>@2     (extensions: prop)
6Midpoints with several arrivalsmidpoint reached at several NIDs

Stations try every arrival NID; all fully-resolving arrivals contribute (landings unioned), otherwise the first arrival showing progress is used. Explicit /@| join midpoints following an intersection get the same candidate search as target joins when the fast path (all sub-branches agree) fails. Unanchored midpoints use junction pinning: a failed sub-branch’s gap ends at the junction a sibling resolved through; if no continuation resolved anywhere, the continuation is duplicated per pair (exploded semantics). prop

7Backward expression is restrictedexpressing a gap backward

Backward-expressed gaps ([@3<~a]>@1) are produced only for EndAt contexts with a pinnable start (loops, pinned roots); gaps starting at Unanchored roots are always forward-expressed since their root must never pin.

examples 
loop, root pins:        [@2>"c">@1, @3>"b">@2]  ⊢  @[a/|b/|c]  ⇒  [@3<~a]>@1
Unanchored, never pins: [@1>"a">@2]             ⊢  [a & b]     ⇒  [b]
8Forward greedy matching, with one exceptionforward and backward passes overlap

Linear runs always consume the longest forward prefix (what the unit tests require — see §1), except: if every consumed forward step left the frontier unchanged (only self-loop matches) and the backward pass from the end was fully rolled back and re-running backward with no forward consumption makes real progress, the backward seam wins. This discriminates coincidental self-loop matches from genuine ones in all tested cases.

greedy baseline 
[@1>"a">@2, @3>"b">@4]  ⊢  [a/|b]>@4  ⇒  [@2<b]>@4            (exception: prop)
9Open-backward matchingfinal run ends open / at a join

§4.1 says an open backward frontier “accepts any landing” but leaves the mode-On behavior open. For the final run of a branch, an open/join end gets a backward pass seeded with every node of the graph; this is what lets [a /| b] recover the seam [a]>@m when only m>"b">f survives (required by property 2). Non-final runs do not — their boundary is recovered structurally (decision 10). prop

10Recovery behind unknown boundariesgap runs into a join midpoint / intersection

When a run gaps into a JoinPoint midpoint or an intersection (whose NID is unknowable), the remaining tail is matched from every graph node (“tail candidates”); if the whole tail resolves somewhere, the gap closes at that seam, otherwise the structure is kept as one connected gap (chaining) — safe for the invariant but not minimal. Structures inside a chained gap are not re-attempted. prop

11Residual assembly orderOMap/OSet insertion order

OMap/OSet equality is insertion-order sensitive, so the tests pin orderings: gaps that consumed something precede gaps re-rooted at their start position; root maps follow branch declaration order; forward fan-outs are in ascending NID order.

§3

Constructive property-test generation 2026-06-10

The property tests originally filtered generated data. Both filters are now replaced by a constructive rewrite, coveredPathFrom (in TestUtils), applied to every generated path.

Before — filtered

  • suchThat (not . requiresUnanchoredJoin) — carve-out paths regenerated until one passes
  • ==> on “the generated graph resolves the path” — whole cases discarded after doing the expensive work
  • failures printed only the removed edges and the residual — undiagnosable after the fact

After — constructive

  • top-level Unanchored target with several terminals → JoinPoint ∅ (the spec’s “append >@” normalization; these paths are now exercised, not skipped)
  • start NID stripped from every JoinPoint exclusion set (a root excluding it can never resolve; real with genNID’s 1–100 range)
  • resolvesIn guards remain as safety nets but essentially never discard; failures now print path, start, and graph via counterexample

§4

Open issue: property 3 genuinely falsifies

pre-existing · ~1 falsification per ~800 cases

The failing path’s target @[~"e" & "d"] is a JoinPoint-with-loops target — a shape the old, filtering generator also produced, so this class of failure predates the constructive generation change (the baseline suite falsified property 3 in roughly half of its 100-case runs).
